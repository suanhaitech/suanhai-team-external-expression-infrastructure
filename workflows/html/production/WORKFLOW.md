# HTML 对外表达制作工作流

状态：`implemented / experimental`

能力 ID：`expression.html-production`

## 目标

把一次 HTML 制作任务组织成可追溯、可预览、可修订和可收口的生产过程。工作流适用于：

- 使用公共小组资产仓模板的消费端；
- 已有自己的目录结构、但已经接入基础设施 submodule 的消费端；
- 使用不同 Agent 客户端的本地工作区。

工作流负责阶段、确认点和边界；模板、组件、预览器和检查器负责具体能力。项目事实、来源文件、素材和评审记录始终留在消费端仓库。

## 输入

- 用户对网页目标的自然语言需求；
- 目标受众、用途、交付形式和预期时间；
- 文档、链接、图片、数据、代码、会议记录等候选材料；
- 消费端仓库的项目上下文、任务目录和发布边界；
- 当前固定 submodule 中 Manifest 声明的能力。

## 场景路由

场景说明为什么表达、面向谁和希望受众发生什么变化；它不是工作流或页面形式。开始任务时先对照 [`scenarios/catalog.json`](../../../scenarios/catalog.json) 识别适用画像，并读取对应 `README.md` 与 `scene.yml`。当前可用画像为：

- `expression.scenario.course-learning-v1`：课程学习，默认输出根 `courses/`，重点是学习目标、概念递进、例子、练习/讨论和迁移；
- `expression.scenario.project-progress-communication-v1`：面向合作方的项目进展沟通，默认输出根 `reports/`，重点是项目总体判断、各工作主线的证据与限制、跨线影响、协作请求和下周期计划。

用户仓库的目录约定优先于场景默认值。用户目标属于已知场景时，在 `html.materialize` 中传入 `--scenario-id`，使场景 ID 与版本进入作品元数据和物料化记录。若没有合适场景，不要强行套用；继续澄清并在任务记录中说明这是未分类/新场景。场景画像只提供内容结构与验收重点，不替负责人核验事实、决定授权或选择唯一页面容器。

用户可以在标准模板仓库或既有仓库中启动流程。工作流不得假定消费端一定有 `reports/`；应先读取消费端 `AGENTS.md`、任务目录约定和可选的 `.suanhai/expression.json`，再结合场景画像登记稳定输出根。课程学习通常使用 `courses/<task-id>`，项目进展沟通通常使用 `reports/<task-id>`；工具按当前修订生成 `v001`、`v002` 等版本目录。旧消费端可以按仓库自身约定使用兼容的 `works/<task-id>`。

## 阶段与停止条件

### 1. 登记任务

Agent 先使用 `expression.task-record` 创建任务，不直接写 HTML。任务至少记录目标、受众、用途、范围、输出位置、完成标准和候选来源。未知项保留为空或标记为待确认，不得猜测。

如果用户只要求调查或比较方案，停在任务澄清或内容结构阶段，不创建页面产物。

### 2. 对齐简报

Agent 主动推荐容器、页面职责和可复用资产，只就现有材料无法确定且会改变用途、范围或授权的问题提问；已认可方案直接执行，不重复确认。Agent 读取来源清单，提出会改变页面方向的问题，并把用户实际确认原话记录到任务历史。至少需要对齐：

- 页面面向谁、用于什么场景；
- 页面要促成读者理解、决定或行动的结果；
- 覆盖的时间范围和内容边界；
- 哪些材料允许使用、哪些材料只供内部核对；
- 交付目录、版本规则和完成标准。

课程学习还要对齐受众已有基础、希望达到的理解深度、时间预算和参与方式。时间预算用于取舍讲解范围、解释深度和讨论时间，不自动换算成固定页数或字数。可参考 [中性简报样例](../../../infrastructure/html/examples/records/brief.json)，辅助简报文件不能成为第二份任务状态。

场景应进一步说明实践/认知对象、表达者希望受众产生的变化、输入证据、参与方式和成功标准。不要把 HTML、PDF、长页或逐页容器写成表达场景；它们分别是交付媒介或阅读容器。

受众、用途、范围或授权发生变化时，按任务循环回到 `clarifying`，不得在旧简报下继续制作。

### 3. 来源、内容结构与场景映射

Agent 为候选来源建立 `sources.yml`，记录路径或 URL、版本/日期、来源类型、使用许可、可引用范围和核对状态。将该清单或其他实际来源文件路径登记到任务简报的 `sources` 中，确保任务工具可以验证来源文件存在。再生成不含项目事实的内容结构：页面目标、章节、语义组件、核心判断和待确认内容。

只有已登记且允许使用的来源才能进入页面；有来源不等于已经核验，用户口述不等于发布授权。

使用图片或衍生图时，按 [`html.source-assets`](../../../infrastructure/html/tools/source-assets/README.md) 准备素材规格：原始图与裁剪、加注等衍生版本分别登记，说明来源、使用边界和转换。工具只核验已经取得的本地文件，不下载 URL 或确认版权。把素材复制到本次版本目录后，先预览 `register`、核对摘要再显式应用；进入评审前以 `validate` 核验文件哈希和衍生关系。语义来源映射与素材字节登记承担不同职责，不能互相替代。

对于项目周期汇报，项目经理是总报告的整合者和主汇报人，不是所有技术事实的唯一来源。先确认汇报周期、数据截止时间、目标受众和披露范围，再从已授权的主线材料或用户提供的信息中收集上期目标、本期结果、证据位置、结论/限制、依赖风险和下周期目标。主线负责人核验各自的事实、数值和专业结论；项目经理核对总体判断、跨线关系、里程碑影响与统一口径。未收到更新或证据不足的内容标记为“待确认”，不得当作无进展或用上一期内容填补；缺少上期基线时明确注明。核验状态记入消费端来源清单或评审记录，不新增一套任务状态机。

对已登记场景，Agent 必须读取其场景画像，并在选择页面资产前形成一份消费端可审阅的逐页计划。计划应覆盖当前整稿，而不是只列本轮新做的页面；至少列出稳定页面 ID、页面目标、核心信息、来源/证据、候选页面职责或资产、场景验收信号。页序、目录与显示页码从当前页面顺序派生，插页时不手工在多处维护序号。场景画像提供决策要求，逐页计划说明本任务如何应用这些要求；不得只设置场景 ID 后直接制作。

使用单页组合时，以 `page-plan.json` 保存可执行的整稿清单，并可另附面向人的 `page-plan.md`。JSON 按 [页面计划样例](../../../infrastructure/html/examples/records/page-plan.json) 和固定版本的 Schema 填写：`pages[].id` 不随页序变化；`template_id` 选择实际资产；`source_ids` 关联已登记来源；需要回应前文时用 `responds_to` 关联已存在的问题页。实际内容填在已声明的 `slots`，不把演示页码写进页面 ID。`artifact_kind` 记录模板或报告；各页用 `candidate_assets`、实际 `template_id/components`、`customization_reason` 和 `acceptance_signals` 记录候选/选用资产、定制理由与验收信号。无需定制时写明复用，无匹配资产时记录缺口。人读视图与可执行清单应一致，不能出现 HTML 已有某页而清单漏页的状态。

逐页来源记录可使用 [source-map.json 样例](../../../infrastructure/html/examples/records/source-map.json)，区分原文定义、来源观察、讲者归纳、教学构造和团队判断，记录具体段落/图号、允许用途、核对状态及待确认项。来源 ID 闭合只证明文件间引用一致，不证明论断正确或获得引用授权。

项目周期汇报的逐页计划应先安排项目经理的总体判断和相对上期变化，再安排工作主线结果/证据/限制、跨线依赖及其对目标/里程碑的影响、需要双方确认或支持的事项、下周期结果与责任安排。总报告负责解释项目整体；较长的技术证据保留在已登记且获准使用的来源或附件中并建立链接，不把各主线原文拼接成一份工作清单。

逐页计划应区分画像中的“必须”“默认建议”和“按需选择”。偏离必须项时先回到简报澄清并记录理由；遇到没有对应模板、组件或交互能力时标记为基础设施缺口，允许在用户知情并确认后采用已有资产完成，但不得把缺口说成已支持能力。逐页计划需在用户确认内容方向后再进入页面资产选择和物料化。

### 4. 选择页面与组件

新任务默认采用分页：`html.container.presentation-deck-v1` + `page-plan.json` + `html.single-page.*`，服务现场逐页讲解。用户明确要求连续阅读、传阅或查阅时选择长页；既有长页版本继续兼容，不自动改版。容器与内容完成度独立：分页或长页都可以交付空白模板（`template`）或已填写报告（`report`）。Agent 应说明推荐理由，不默认要求用户自行选择技术组件。

Agent 从当前 Manifest 选择已实现的页面模板和组件包，读取其入口文档与元数据。选择依据是任务的受众、用途和内容结构，不根据模板名称猜测能力。

- 读者需要连续向下阅读、浏览多个章节，或主要作为网页文档查阅时，选择 `html.project-report-v1` 这个长页组合预设；
- 需要按讲解节奏逐页呈现、在现场演示中切换，或要求导出为逐页打印材料时，选择 `html.presentation-deck-v1` 这个演示稿组合预设；
- 如果当前 Manifest 已登记单页模板，先选择 `html.container.presentation-deck-v1`，再按页面顺序选择封面、目录、章节过渡、内容、结尾和附录页面；页面变体必须声明与容器的兼容关系，不能仅凭目录名称猜测。初步结构可使用 `html.materialize --container-id ... --page-id ...`，每个 `--page-id` 的顺序就是展示顺序；页面可以重复。需要稳定页面 ID、来源、备注、组件和局部修订时，使用 `--page-plan <消费端相对路径>` 传入完整清单，与 `--page-id` 互斥。只使用模板已声明的组件插槽，不向组合模式传预设专用的顶层 `--component-id`。
- 页面选择必须落实已确认的逐页计划：课程按学习者理解顺序组织，项目进展沟通按总体判断、主线证据、跨线影响和行动顺序组织。场景画像是内容模型，容器是阅读方式，单页模板是表达结构，不能互相替代。场景本身不自动决定模板、主题样式或交互。
- 演示稿使用页面底部的页码选择、上一页和下一页切换，不以顶部导航切页；每页聚焦一个判断或问题。正文保留核心信息和影响结论的必要条件；扩展解释、串场与完整出处可放默认隐藏的备注，详细证据和完整来源可放附录/source-map，不强制每页显示来源小字。备注随文件交付，展开时投屏也可见，不是独立讲者视图；
- 完整预设可以通过 `--component-id` 把语义片段放入模板插槽；单页组合通过页面计划中 `components` 指定实际已声明的页面插槽。组合后核对稳定 ID、顺序、目录页码、标题和来源追溯；页面比例是首选尺寸，长内容不得裁剪，要求一页一纸时先拆页再检查导出结果；
- 演示稿的翻页、手动比例、备注和逐页打印由模板自带，不依赖 `html.runtime-kit-v1`。新物料化默认装配工具栏/公式包与原图阅读器，已有独立模板和低层插槽 API 继续兼容。

组件和运行时选择应记录在 `report.yml` 中。先选择 Manifest 中的组件包，再从其 `index.yml` 选择稳定的语义组件 ID；交互组件指全屏、保存 PDF、显示模式、翻页、比例、备注和原图阅读；它们默认配齐、增量扩展，由 Agent 主动介绍用途与限制，无需用户逐项指定。物料化工具会把选中的片段插入页面的组件插槽，并同时复制完整组件包和运行时包，后续可按契约继续调整。上述片段属于语义组件，与交互组件分开理解；每个语义组件应能关联来源状态、响应式行为和无障碍要求。

当 Manifest 注册 `html.materialize` 时，应调用 `infrastructure/html/tools/materialize/materialize_html.py` 物料化已选模板、响应式布局包、运行时包和组件，不要逐文件手工复制。已登记场景应传入 `--scenario-id <场景 ID>`；该值只作作品分类与溯源，不改变已对齐的任务输出路径。需要响应式布局时传入 `--layout-id html.responsive-layout-v1`，默认运行时集合自动装配；额外的已注册运行时通过 `--runtime-kit-id` 增量添加。先 dry-run，核对目标目录、能力版本和基础设施 commit，再把预览返回的 `plan_sha256` 与 `task_record_version` 一并传给 `--apply`。工具要求任务已进入 `working`，并从已经对齐的 `brief.output` 推导任务修订路径。遇到缺少能力、路径不匹配、gitlink 不一致或目标冲突时停止，不绕开工具直接复制。

新单页的公共页框由 `shared_styles` 声明并随作品复制；可按需显式选择 `--layout-id html.presentation-foundation-v1`，暖白主题使用 `--theme editorial-warm`，不复制一套私有排版。布局包与运行时包参数均可重复。原图阅读器默认装配，按其入口标记本地原图链接；它提供适应窗口、原始尺寸、缩放、拖动、关闭和焦点管理。没有图片时不制造无效入口；原图编辑不在当前范围。

### 5. 生成首版

Agent 在消费端任务目录创建 `v001`，至少包含：

```text
<输出根>/<task-id>/v001/
├── report.yml
├── index.html
├── assets/
├── sources.yml
└── README.md
```

HTML 和 CSS 使用相对路径，资源自包含，不依赖 CDN、远程字体、远程图片或运行时网络服务。物料化结果中的 `materialization.json` 保留共享资产来源 commit 与文件哈希；完整报告必须用有来源的内容替换模板占位；空白模板保留明确占位，不把占位文字当作项目事实。两者均遵守[模板填写与复用协议](../../../infrastructure/html/templates/FILLING.md)，清理对读者无用的作者提示，填写正文、状态属性和可见标签，并提供重复单元与隔离合成填写验证。

默认装配后，页面可用 `<span data-math="...">` 或带 `data-math-display="block"` 的元素表达公式；运行时使用随包锁定的 KaTeX，失败时保留 TeX 源文本。页面工具栏可切换自动、窄屏、平板和桌面模式，可进入/退出全屏，也可打开浏览器打印对话框保存 PDF。手动模式只改变页面 CSS，不模拟 viewport；确定性 PDF 仍必须调用 `html.pdf-export`。

### 6. 响应式检查、预览与 PDF

Agent 在首版生成后调用 Manifest 中的 `html.viewport-check`，执行默认的窄竖屏、平板、桌面、宽屏和 A4 检查。浏览器后端可用 Playwright 或本机 Chrome、Edge、Chromium 的 CDP；`--backend auto` 优先尝试 Playwright，不可用时尝试 CDP。按交付类型显式传入 `--artifact-kind template|report`。演示稿传入 `--all-pages --interactions --full-page --fail-on-overflow`，遍历整稿并检查实际交互，不能用首张截图代替全部页面。逐页检查报告中的 `pageVerticalOverflow` 表示该页内容超过可视画布、需要在页内滚动；应压缩信息、调整版式或拆成多页后重检，不能隐藏溢出、删去必要事实或仅把页面滚动当作展示完成。`navigationOverlap` 表示可读内容与固定控制栏发生几何相交，必须先解决遮挡再评审。浏览器均不可用时保留 `not-run`，不能把静态检查写成视觉通过。用户需要交付 PDF 时，在 viewport 检查完成且用户确认导出参数后调用 `html.pdf-export`，生成 `pdf-export.json` 和 PDF；找不到 Chrome、Edge 或 Chromium 时明确停在 `not-run`。

需要整体审阅时用 `--screenshot-dir <本轮截图目录> --contact-sheet <本轮图册.html>` 生成离线截图联系表；可通过 `--compare-with <旧检查JSON>` 按视口与页序并排展示新旧截图。插页或重排后人工确认对应关系，工具不自动判断审美、内容等价或用户认可。长页也用 `--interactions --full-page` 检查锚点目标并保留全长截图；滚动定位与焦点仍人工核验。实际结果保存 HTML 摘要、实际引用资源集摘要、逐项状态、证据和限制；统一结果契约见 [check-result.schema.json](../../../infrastructure/html/schemas/check-result.schema.json)。

Agent 生成本地预览或截图，至少检查桌面、手机和打印视图。用户反馈按以下类别记录：内容、事实/来源、结构、视觉、屏幕适配、打印/无障碍和范围变化。

经授权升级基础设施后，已在 review/ready 的旧任务可用 `event --type feedback --infrastructure-commit <新SHA> --user-quote <真实原话>` 开始新修订；先提交父仓 gitlink，工具核对当前 submodule 干净且一致，历史作品保留原来源。不得直接编辑 task.json 或在同一修订中换版。

局部反馈生成新版本目录，例如 `v002`，不得覆盖旧版本；范围变化必须回到澄清阶段。反馈记录应列出目标页面稳定 ID、基线版本、允许改变的内容或样式，以及要求保留的认可范围，可参考 [revision.json 样例](../../../infrastructure/html/examples/records/revision.json)。实际用户原话保存到任务事件，示例文案不能当作真实认可。

固定版本的工具支持局部修订时，传完整 `--page-plan` 并使用 `--baseline-version v001 --replace-page <页面 ID>`（多页重复该参数），先核对 dry-run，再应用同一计划。基线只读；目标范围外的页面、资源和认可内容应继承，并以摘要/差异检查验证。工具能发现非目标内容变化，不能自动判断页面已被用户认可，也不能把需要全局改版的请求伪装成局部替换。浏览器运行时不可用时，必须明确报告 `not-run`，不能宣称已完成视觉验证。

### 7. 检查与评审

Agent 在进入 `review` 前执行当前已实现的检查：文件存在、路径在任务目录内、来源 ID 闭合、HTML 结构和本地资源可解析，并保存 `html.viewport-check` 的静态结果；如果 Playwright 或本机 CDP 可用，再保存整稿真实视口与交互结果。存在已登记素材时运行 `html.source-assets validate`；用户要求 PDF 时，还要保存 `html.pdf-export` 的元数据。无障碍和公式专用检查尚未注册，必须把这两个缺口保留在评审限制中。

检查通过不代表专业事实正确，也不代表对外发布授权。Chaos 或消费端负责人分别完成项目事实、表达质量、公式可读性、显示模式、全屏交互和 PDF 打印结果以及发布授权确认。

项目周期汇报中，各主线负责人核验本线事实和专业内容；项目经理检查总判断、跨线依赖、里程碑影响、协作请求和下周期安排是否与来源一致。核验状态保存在消费端来源清单或评审记录中，未核验的结论继续标记为待确认。主汇报人身份本身不构成发布授权。

### 8. 收口与续作

只有用户明确确认本轮约定的完整交付范围，才能使用任务循环记录确认原话、产出路径、SHA-256 和仍存限制，再进入 `completed`。认可封面或某一页、同意继续制作、授权提交/推送，都不自动等于整课验收或发布授权。

分阶段制作应登记已制作页、占位页和已讨论未制作部分。用户要求今天暂停时使用现有 `pause`，记录最新版本、认可范围、检查限制和下一步；续作先 `show` 并核对文件与摘要，再 `resume`，不重建同名任务或另一套状态。可参考 [handoff.md 样例](../../../infrastructure/html/examples/records/handoff.md)。以后通过任务编号恢复；新一轮修订保留历史版本并使用新的 `vNNN` 目录。

## 不得做的事情

- 不得在没有任务简报和来源边界时直接生成对外页面；
- 不得把项目专属事实、客户材料或未经授权的素材写入基础设施 submodule；
- 不得自动跟随 submodule 远端分支或擅自升级依赖；
- 不得覆盖已经评审或确认的版本；
- 不得因为 HTML 检查通过就宣称已经获得发布授权；
- 不得自动提交、推送、部署或发布，除非用户另行明确授权。

## 周期汇报的资产选择与局部检查

项目进展场景需要展开表达时，读取[周期汇报资产与填写规则](../../../docs/project-report-reusable-assets.md)。先分来源提取事实，依页面责任选择状态面板与主线展开页；用“任务／交付／如何核对”检查计划。主稿和附件分层，影响判断的限制留正文。选主题后检查封面、过渡、内容和控件颜色一致，不复制黄绿两套结构。

增删重排后依据稳定页面ID核对目录、显示页码、导航选项、逐页计划与来源映射。检查证据记录当前HTML及有效CSS/JS摘要，旧证据仅作历史；初次materialization.json保留出厂来源，不改写摘要制造未定制的假象。这是记录要求，不表示工具已经自动核对所有后续手改资源。
