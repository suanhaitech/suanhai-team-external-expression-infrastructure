# HTML 对外表达制作工作流

状态：`implemented / experimental`

能力 ID：`expression.html-production`

## 目标

把一次 HTML 制作任务组织成可追溯、可预览、可修订和可收口的生产过程。工作流适用于：

- 使用公共小组资产仓模板的消费端；
- 已有自己的目录结构、但已经接入基础设施 submodule 的消费端；
- 使用不同 Agent 客户端的本地工作区。

工作流负责阶段、确认点和边界；模板、组件、预览器和检查器负责具体能力。项目事实、来源文件、素材和评审记录始终留在消费端仓库。

## 输入

- 用户对网页目标的自然语言需求；
- 目标受众、用途、交付形式和预期时间；
- 文档、链接、图片、数据、代码、会议记录等候选材料；
- 消费端仓库的项目上下文、任务目录和发布边界；
- 当前固定 submodule 中 Manifest 声明的能力。

## 场景路由

场景说明为什么表达、面向谁和希望受众发生什么变化；它不是工作流或页面形式。开始任务时先对照 [`scenarios/catalog.json`](../../../scenarios/catalog.json) 识别适用画像，并读取对应 `README.md` 与 `scene.yml`。当前可用画像为：

- `expression.scenario.course-learning-v1`：课程学习，默认输出根 `courses/`，重点是学习目标、概念递进、例子、练习/讨论和迁移；
- `expression.scenario.project-progress-communication-v1`：面向合作方的项目进展沟通，默认输出根 `reports/`，重点是阶段、工作主线、证据、风险、依赖和下一步。

用户仓库的目录约定优先于场景默认值。用户目标属于已知场景时，在 `html.materialize` 中传入 `--scenario-id`，使场景 ID 与版本进入作品元数据和物料化记录。若没有合适场景，不要强行套用；继续澄清并在任务记录中说明这是未分类/新场景。场景画像只提供内容结构与验收重点，不替负责人核验事实、决定授权或选择唯一页面容器。

用户可以在标准模板仓库或既有仓库中启动流程。工作流不得假定消费端一定有 `reports/`；应先读取消费端 `AGENTS.md`、任务目录约定和可选的 `.suanhai/expression.json`，再结合场景画像登记稳定输出根。课程学习通常使用 `courses/<task-id>`，项目进展沟通通常使用 `reports/<task-id>`；工具按当前修订生成 `v001`、`v002` 等版本目录。旧消费端可以按仓库自身约定使用兼容的 `works/<task-id>`。

## 阶段与停止条件

### 1. 登记任务

Agent 先使用 `expression.task-record` 创建任务，不直接写 HTML。任务至少记录目标、受众、用途、范围、输出位置、完成标准和候选来源。未知项保留为空或标记为待确认，不得猜测。

如果用户只要求调查或比较方案，停在任务澄清或内容结构阶段，不创建页面产物。

### 2. 对齐简报

Agent 读取来源清单，提出会改变页面方向的问题，并把用户实际确认原话记录到任务历史。至少需要对齐：

- 页面面向谁、用于什么场景；
- 页面要促成读者理解、决定或行动的结果；
- 覆盖的时间范围和内容边界；
- 哪些材料允许使用、哪些材料只供内部核对；
- 交付目录、版本规则和完成标准。

课程学习还要对齐受众已有基础、希望达到的理解深度、时间预算和参与方式。时间预算用于取舍讲解范围、解释深度和讨论时间，不自动换算成固定页数或字数。可参考 [中性简报样例](../../../infrastructure/html/examples/records/brief.json)，辅助简报文件不能成为第二份任务状态。

场景应进一步说明实践/认知对象、表达者希望受众产生的变化、输入证据、参与方式和成功标准。不要把 HTML、PDF、长页或逐页容器写成表达场景；它们分别是交付媒介或阅读容器。

受众、用途、范围或授权发生变化时，按任务循环回到 `clarifying`，不得在旧简报下继续制作。

### 3. 来源、内容结构与场景映射

Agent 为候选来源建立 `sources.yml`，记录路径或 URL、版本/日期、来源类型、使用许可、可引用范围和核对状态。将该清单或其他实际来源文件路径登记到任务简报的 `sources` 中，确保任务工具可以验证来源文件存在。再生成不含项目事实的内容结构：页面目标、章节、语义组件、核心判断和待确认内容。

只有已登记且允许使用的来源才能进入页面；有来源不等于已经核验，用户口述不等于发布授权。

对已登记场景，Agent 必须读取其场景画像，并在选择页面资产前形成一份消费端可审阅的逐页计划。计划应覆盖当前整稿，而不是只列本轮新做的页面；至少列出稳定页面 ID、页面目标、核心信息、来源/证据、候选页面职责或资产、场景验收信号。页序、目录与显示页码从当前页面顺序派生，插页时不手工在多处维护序号。场景画像提供决策要求，逐页计划说明本任务如何应用这些要求；不得只设置场景 ID 后直接制作。

使用单页组合时，以 `page-plan.json` 保存可执行的整稿清单，并可另附面向人的 `page-plan.md`。JSON 按 [页面计划样例](../../../infrastructure/html/examples/records/page-plan.json) 和固定版本的 Schema 填写：`pages[].id` 不随页序变化；`template_id` 选择实际资产；`source_ids` 关联已登记来源；需要回应前文时用 `responds_to` 关联已存在的问题页。实际内容填在已声明的 `slots`，不把演示页码写进页面 ID。人读视图与可执行清单应一致，不能出现 HTML 已有某页而清单漏页的状态。

逐页来源记录可使用 [source-map.json 样例](../../../infrastructure/html/examples/records/source-map.json)，区分原文定义、来源观察、讲者归纳、教学构造和团队判断，记录具体段落/图号、允许用途、核对状态及待确认项。来源 ID 闭合只证明文件间引用一致，不证明论断正确或获得引用授权。

逐页计划应区分画像中的“必须”“默认建议”和“按需选择”。偏离必须项时先回到简报澄清并记录理由；遇到没有对应模板、组件或交互能力时标记为基础设施缺口，允许在用户知情并确认后采用已有资产完成，但不得把缺口说成已支持能力。逐页计划需在用户确认内容方向后再进入页面资产选择和物料化。

### 4. 选择页面与组件

Agent 从当前 Manifest 选择已实现的页面模板和组件包，读取其入口文档与元数据。选择依据是任务的受众、用途和内容结构，不根据模板名称猜测能力。

- 读者需要连续向下阅读、浏览多个章节，或主要作为网页文档查阅时，选择 `html.project-report-v1` 这个长页组合预设；
- 需要按讲解节奏逐页呈现、在现场演示中切换，或要求导出为逐页打印材料时，选择 `html.presentation-deck-v1` 这个演示稿组合预设；
- 如果当前 Manifest 已登记单页模板，先选择 `html.container.presentation-deck-v1`，再按页面顺序选择封面、目录、章节过渡、内容、结尾和附录页面；页面变体必须声明与容器的兼容关系，不能仅凭目录名称猜测。初步结构可使用 `html.materialize --container-id ... --page-id ...`，每个 `--page-id` 的顺序就是展示顺序；页面可以重复。需要稳定页面 ID、来源、备注、组件和局部修订时，使用 `--page-plan <消费端相对路径>` 传入完整清单，与 `--page-id` 互斥。只使用模板已声明的组件插槽，不向组合模式传预设专用的顶层 `--component-id`。
- 页面选择必须落实已确认的逐页计划：课程按学习者理解顺序组织，项目进展沟通按状态与证据顺序组织。场景画像是内容模型，容器是阅读方式，单页模板是表达结构，不能互相替代。场景本身不自动决定模板、主题样式或交互。
- 演示稿使用页面底部的页码选择、上一页和下一页切换，不以顶部导航切页；每页聚焦一个判断或问题。正文保留核心信息和影响结论的必要条件；扩展解释、串场与完整出处可放默认隐藏的备注，详细证据和完整来源可放附录/source-map，不强制每页显示来源小字。备注随文件交付，不是保密区域；
- 完整预设可以通过 `--component-id` 把语义片段放入模板插槽；单页组合通过页面计划中 `components` 指定实际已声明的页面插槽。组合后核对稳定 ID、顺序、目录页码、标题和来源追溯；页面比例是首选尺寸，长内容不得裁剪，要求一页一纸时先拆页再检查导出结果；
- 演示稿的翻页、手动比例、备注和逐页打印由模板自带，不依赖 `html.runtime-kit-v1`。该运行时仅在页面还需要公式渲染、全屏、显示模式或浏览器打印按钮时选用。

组件和运行时选择应记录在 `report.yml` 中。先选择 Manifest 中的组件包，再从其 `index.yml` 选择稳定的语义组件 ID；需要公式、页面显示模式、全屏或浏览器保存 PDF 入口时选择 `html.runtime-kit-v1`。物料化工具会把选中的片段插入页面的组件插槽，并同时复制完整组件包和运行时包，后续可按契约继续调整。组件是语义信息对象，不是任意视觉卡片；每个组件应能关联来源状态、响应式行为和无障碍要求。

当 Manifest 注册 `html.materialize` 时，应调用 `infrastructure/html/tools/materialize/materialize_html.py` 物料化已选模板、响应式布局包、运行时包和组件，不要逐文件手工复制。已登记场景应传入 `--scenario-id <场景 ID>`；该值只作作品分类与溯源，不改变已对齐的任务输出路径。需要响应式布局时传入 `--layout-id html.responsive-layout-v1`，需要运行时能力时传入 `--runtime-kit-id html.runtime-kit-v1`。先 dry-run，核对目标目录、能力版本和基础设施 commit，再把预览返回的 `plan_sha256` 与 `task_record_version` 一并传给 `--apply`。工具要求任务已进入 `working`，并从已经对齐的 `brief.output` 推导任务修订路径。遇到缺少能力、路径不匹配、gitlink 不一致或目标冲突时停止，不绕开工具直接复制。

### 5. 生成首版

Agent 在消费端任务目录创建 `v001`，至少包含：

```text
<输出根>/<task-id>/v001/
├── report.yml
├── index.html
├── assets/
├── sources.yml
└── README.md
```

HTML 和 CSS 使用相对路径，资源自包含，不依赖 CDN、远程字体、远程图片或运行时网络服务。物料化结果中的 `materialization.json` 保留共享资产来源 commit 与文件哈希；模板占位内容必须被真实内容替换，不能把占位文字当作项目事实。

选择 `html.runtime-kit-v1` 后，页面可用 `<span data-math="...">` 或带 `data-math-display="block"` 的元素表达公式；运行时使用随包锁定的 KaTeX，失败时保留 TeX 源文本。页面工具栏可切换自动、窄屏、平板和桌面模式，可进入/退出全屏，也可打开浏览器打印对话框保存 PDF。手动模式只改变页面 CSS，不模拟 viewport；确定性 PDF 仍必须调用 `html.pdf-export`。

### 6. 响应式检查、预览与 PDF

Agent 在首版生成后调用 Manifest 中的 `html.viewport-check`，执行默认的窄竖屏、平板、桌面、宽屏和 A4 检查。若本机具备 Playwright 浏览器运行时，可生成视口截图；否则保留 `not-run`，不能把静态检查写成视觉通过。用户需要交付 PDF 时，在 viewport 检查完成且用户确认导出参数后调用 `html.pdf-export`，生成 `pdf-export.json` 和 PDF；找不到 Chrome、Edge 或 Chromium 时明确停在 `not-run`。

Agent 生成本地预览或截图，至少检查桌面、手机和打印视图。用户反馈按以下类别记录：内容、事实/来源、结构、视觉、屏幕适配、打印/无障碍和范围变化。

局部反馈生成新版本目录，例如 `v002`，不得覆盖旧版本；范围变化必须回到澄清阶段。反馈记录应列出目标页面稳定 ID、基线版本、允许改变的内容或样式，以及要求保留的认可范围，可参考 [revision.json 样例](../../../infrastructure/html/examples/records/revision.json)。实际用户原话保存到任务事件，示例文案不能当作真实认可。

固定版本的工具支持局部修订时，传完整 `--page-plan` 并使用 `--baseline-version v001 --replace-page <页面 ID>`（多页重复该参数），先核对 dry-run，再应用同一计划。基线只读；目标范围外的页面、资源和认可内容应继承，并以摘要/差异检查验证。工具能发现非目标内容变化，不能自动判断页面已被用户认可，也不能把需要全局改版的请求伪装成局部替换。浏览器运行时不可用时，必须明确报告 `not-run`，不能宣称已完成视觉验证。

### 7. 检查与评审

Agent 在进入 `review` 前执行当前已实现的检查：文件存在、路径在任务目录内、来源 ID 闭合、HTML 结构和本地资源可解析，并保存 `html.viewport-check` 的静态结果；如果本机具备 Playwright，再保存真实视口结果。用户要求 PDF 时，还要保存 `html.pdf-export` 的元数据。无障碍和公式检查尚未注册，必须把这两个缺口保留在评审限制中。

检查通过不代表专业事实正确，也不代表对外发布授权。Chaos 或消费端负责人分别完成项目事实、表达质量、公式可读性、显示模式、全屏交互和 PDF 打印结果以及发布授权确认。

### 8. 收口与续作

只有用户明确确认本轮约定的完整交付范围，才能使用任务循环记录确认原话、产出路径、SHA-256 和仍存限制，再进入 `completed`。认可封面或某一页、同意继续制作、授权提交/推送，都不自动等于整课验收或发布授权。

分阶段制作应登记已制作页、占位页和已讨论未制作部分。用户要求今天暂停时使用现有 `pause`，记录最新版本、认可范围、检查限制和下一步；续作先 `show` 并核对文件与摘要，再 `resume`，不重建同名任务或另一套状态。可参考 [handoff.md 样例](../../../infrastructure/html/examples/records/handoff.md)。以后通过任务编号恢复；新一轮修订保留历史版本并使用新的 `vNNN` 目录。

## 不得做的事情

- 不得在没有任务简报和来源边界时直接生成对外页面；
- 不得把项目专属事实、客户材料或未经授权的素材写入基础设施 submodule；
- 不得自动跟随 submodule 远端分支或擅自升级依赖；
- 不得覆盖已经评审或确认的版本；
- 不得因为 HTML 检查通过就宣称已经获得发布授权；
- 不得自动提交、推送、部署或发布，除非用户另行明确授权。

## 依赖

- `expression.task-loop`
- `expression.task-record`
- `html.project-report-v1`、`html.presentation-deck-v1` 或当前 Manifest 中已登记的容器/单页模板；
- 当前 Manifest 中已实现的 HTML 组件、响应式布局、运行时包、物料化、视口检查和 PDF 导出能力。
