# 项目经理主汇报的项目进展沟通设计

本说明为“面向合作方的项目进展沟通”提供内容设计依据：由项目经理制作一份总报告，组织项目整体判断、工作主线证据、跨线影响与需要采取的行动。项目事实、来源、责任人、真实报告及评审记录留在消费端。本仓只沉淀可复用的职责、页面结构和检查方法。

## 1. 三层关系与适用范围

| 层次 | 本设计中的职责 | 既有入口 |
| --- | --- | --- |
| 场景画像 | 定义受众需要理解什么、需要确认什么，以及如何判断沟通有效 | `expression.scenario.project-progress-communication-v1` |
| 工作流 | 组织来源登记、内容计划、页面选择、制作、检查、反馈与收口 | `expression.html-production` |
| 页面基础设施 | 为总体判断、主线更新、依赖和行动提供可组合的表达结构 | 当前固定 Manifest 中的容器与单页模板 |

本设计沿用既有 HTML 制作工作流，不新建“项目经理汇报工作流”，也不另建一整套固定页面预设。场景决定内容责任，工作流决定制作过程，页面模板承载信息；单独增加一个模板不能解决事实缺失或判断未对齐的问题。

与课程学习画像相比，两者共享来源、版本、离线资源和工程检查规则，但内容路径不同。课程主要帮助学习者理解概念、形成判断并迁移应用；项目进展沟通主要帮助合作方理解项目相对目标的变化、证据与限制，并完成必要的协作确认与后续行动。正式方案评审或要求对方作出正式决定属于其他场景。同一个逐页容器可以服务两种场景，无需把容器当成场景。

## 2. 主汇报人的职责边界

项目经理承担总报告的整合与讲述责任，应回答：项目正向哪个目标推进，本周期改变了什么，这些变化为什么重要，哪些问题影响共同目标，接下来需要谁采取什么行动。

| 角色 | 需要负责的判断 | 不能自动替代的责任 |
| --- | --- | --- |
| 工作主线负责人 | 本线事实、数值、专业结论、证据条件和已知限制的核验 | 项目整体判断、跨线承诺及发布授权 |
| 项目经理 / 主汇报人 | 目标与周期边界、总体判断、上期计划对照、跨线影响、里程碑和协作请求的一致性 | 各专业领域的事实核验，以及未获授权的对外发布决定 |
| Agent | 整理来源、发现缺口或冲突、提出内容结构、制作页面和执行工程检查 | 专业结论的责任主体和发布授权主体 |
| 发布责任主体 | 面向特定受众、用途和内容范围的发布决定 | 不能仅凭页面制作完成或工程检查通过推定批准 |

一份总报告可以由多人提供材料，由一人统一讲述。总报告不要求项目经理复述每个技术细节，而要求其理解各条结论如何共同支持项目判断。来源不一致时，应保留冲突和待核对责任人；未收到更新应记为“待确认”，不能解释成“没有进展”，也不能沿用上一期状态填补。

## 3. 从历史样例提炼的结构演进

既往周期报告体现了四个可复用的改进方向：

1. **分主题轮报。**不同主题分别介绍所做工作，便于专业人员说明细节；总报告仍需要补充项目级关联，避免听众自己拼接结论。
2. **统一总体判断。**先说明目标、本周期变化和当前阶段，再进入各主题，让听众有共同的理解框架。
3. **证据与边界分开表达。**把“做了什么、看到了什么、据此能判断什么、还不能判断什么”区分开，防止把原型、单次观察或计划写成稳定能力。
4. **说明跨线影响。**从并列介绍进展，推进到解释一条主线的输入、结果和风险如何影响另一条主线及共同里程碑，并形成可行动的请求。

因此，总报告应按“整体判断 → 主线结果与证据 → 跨线影响 → 协作和下周期结果”组织。较长的技术方法、实验记录和原始数据保留在获准使用的附件或来源中；正文提供可追溯的入口。材料的叙事顺序与团队成员名单不必一致。

## 4. 推荐页面组合

默认使用 `html.container.presentation-deck-v1`，依次组合下表页面。长页阅读需求仍可选既有长页报告预设；内容责任保持一致，不要求复制演示稿的分页。

表中的“必须”约束内容是否覆盖；“默认”表示通常采用，但可在内容计划中说明省略理由；“可选”由材料复杂度和会议时间决定。不是每项内容都必须独占一页，必要时可以拆成多页，不能为了固定页数压缩或裁切重要信息。

| 顺序 | 页面简写 / 完整能力 ID | 必要性 | 主要回答的问题 |
| --- | --- | --- | --- |
| 1 | `cover.editorial` / `html.single-page.cover.editorial-v1` | 默认 | 这是谁面向谁、覆盖哪个周期的汇报，核心主题是什么？ |
| 2 | `content.project-overview-v1` / `html.single-page.content.project-overview-v1` | 必须覆盖总体判断 | 当前目标、相对上期的变化、里程碑状态和主要风险是什么？ |
| 3…n | `content.workstream-update-v1` / `html.single-page.content.workstream-update-v1` | 必须覆盖相关工作主线；可重复 | 上期计划是什么，本期实际形成什么结果，证据与适用边界是什么，对项目有什么影响？ |
| n+1 | `content.dependencies-v1` / `html.single-page.content.dependencies-v1` | 默认；存在影响目标或里程碑的跨线依赖时必须覆盖 | 谁向谁提供什么输入，当前缺口如何影响共同目标，需要如何衔接？ |
| n+2 | `closing.action` / `html.single-page.closing.action-v1` | 必须覆盖行动与下周期安排 | 需要谁在何时完成什么确认或输入，不解决有什么影响，下周期将交付什么可观察结果？ |
| n+3 | `appendix.source-register` / `html.single-page.appendix.source-register-v1` | 默认；来源记录必须保留 | 关键判断依据哪些来源，版本、核验状态和使用范围如何定位？ |
| 按需插入 | 当前 Manifest 中的目录、过渡、证据、方法等单页 | 可选 | 是否需要导航、解释关键方法，或为复杂结论提供一页独立证据？ |

三种项目正文页已通过既有单页契约实现并在 Manifest 登记。消费端只能调用其固定 submodule 版本中已真实登记的能力，不能仅因本说明列出 ID 就认为可用。若当前版本缺页，先在内容计划中记录缺口，再通过已有资产承载相同内容责任。

工作主线更新页可以重复使用，不要求固定三条主线。没有适用的跨线依赖时，可省略独立依赖页并记录判断依据；存在关键依赖时，即使合并到其他页面，也必须保留关联方向、输入、影响和行动。来源附录不能替代逐项来源关联，关键判断在正文或备注中仍应能追溯到来源 ID。

## 5. 会前准备的输入

先收集内容，再选择版式。项目经理需要准备一份共同简报，工作主线负责人提供按统一字段整理的更新，Agent 据此发现空缺与冲突。

| 输入组 | 最小字段 | 处理缺失或变化的方式 |
| --- | --- | --- |
| 汇报边界 | 周期起止、数据截止时间、受众、用途、主汇报人、可披露范围 | 时间或用途改变时重核来源有效性与披露范围 |
| 共同目标 | 当前阶段目标、里程碑、原定可观察结果、现状判断及依据 | 未定义验收口径时保留待确认，不制造完成率 |
| 上期计划对照 | 上期目标及来源、本期实际结果、完成/部分完成/未完成/调整、差异原因及影响 | 计划变化与延期分开说明，不用“已开展工作”替代“达成结果” |
| 各线更新 | 本期结果、证据 ID/版本、结论、适用条件、限制、专业核验人和核验状态 | 无更新或证据不足标记待确认，保留补充责任人 |
| 跨线关联 | 提供方、接收方、所需输入/接口、当前状态、依赖时间、受影响目标或里程碑 | 不凭主题相近推断依赖；注明依据与待核对处 |
| 协作请求 | 谁、需要完成什么动作或提供什么输入、何时需要、未解决的影响 | 尚未达成的请求写成待确认，不写成对方承诺 |
| 下周期安排 | 可观察结果、验收信号、责任方、目标时间、前置条件 | 区分可控计划和依赖外部输入的候选安排 |
| 来源与评审 | 来源定位/日期/版本、事实状态、适用范围、专业核验状态、表达授权范围 | 来源存在、事实核验和发布许可分别记录 |

总体判断应由这些输入共同支持。可以写“在限定条件下取得阶段结果，但某项接口仍阻塞下一里程碑”，不能只用“整体顺利”概括，也不能将各线状态平均成一个没有依据的完成百分比。

### 判断与证据的表达责任

每个关键结论应能沿“判断 → 证据 → 解释 → 适用边界 → 项目影响”追溯。标题优先写可被追问的判断，一张证据页只设一个主判断，互相独立的判断拆页；封面、目录等页面不虚构结论。同一个判断可以有多项互补证据，逐项说明材料版本、具体定位以及它支持的部分，不让听众从没有解释的图里自行推断。

设计成果可以构成阶段结论，但要说明设计覆盖范围、评审状态和下一项实现核验；风险写成触发条件、可能后果与核验动作；程序或任务达到终止状态也不能替代独立质量验收。总体状态须与已知的实现、精度、覆盖或依赖缺口一致，不能用“无重大风险”抵消具体限制。

开场优先提炼少量总体判断，收尾回到判断、缺口和行动，不要求固定三句话或独立总结页。演示稿的 `pages[].notes` 可记录串场提示、关键数字、可能追问及答复来源；必要结论边界仍留正文。备注随 HTML 交付且展开时可能投屏可见，不能放未获准披露的信息。

## 6. 消费端可复制的匿名内容计划

下表是待填写的计划骨架，所有方括号内容和示例来源 ID 都是占位，不代表任何真实项目事实。复制到消费端任务记录后，先用实际来源替换占位，再由项目经理核对叙事顺序；页面制作前完成内容方向对齐。

| 页序 | 页面目标 | 核心信息 / 待填内容 | 来源或证据 | 候选页面 | 验收信号 |
| --- | --- | --- | --- | --- | --- |
| 1 | 确立会议边界 | 〔项目主题〕、〔周期〕、〔数据截止时间〕、〔主汇报人〕、〔沟通目标〕 | 〔已对齐任务简报〕 | `cover.editorial` | 受众能知道本次范围与希望完成的沟通结果 |
| 2 | 给出项目整体判断 | 〔目标〕；〔上期计划与本期结果的关键变化〕；〔里程碑影响〕；〔主要风险〕 | `〔source.overview〕`、`〔source.previous-plan〕` | `content.project-overview-v1` | 判断有依据，变化能与上期目标对照 |
| 3 | 解释工作主线甲的贡献 | 〔上期目标〕→〔本期实际结果〕；〔证据〕；〔结论/限制〕；〔对整体目标的影响〕 | `〔source.line-a〕`、〔核验状态〕 | `content.workstream-update-v1` | 能区分结果、证据、判断和限制 |
| 4 | 解释工作主线乙的贡献 | 〔上期目标〕→〔本期实际结果〕；〔差异原因〕；〔证据/限制〕；〔下一步结果〕 | `〔source.line-b〕`、〔核验状态〕 | `content.workstream-update-v1` | 未完成或调整内容没有被新工作清单掩盖 |
| 5 | 说明跨线影响 | 〔甲提供给乙的输入〕；〔缺口与期限〕；〔受影响里程碑〕；〔衔接动作与责任方〕 | `〔source.dependency〕` | `content.dependencies-v1` | 能沿依赖方向追溯到具体输入和共同目标 |
| 6 | 收敛到协作与下周期结果 | 〔谁〕于〔何时〕完成〔什么〕，否则〔影响〕；下周期〔结果/验收信号/责任方/前置条件〕 | `〔source.action〕`、`〔source.next-plan〕` | `closing.action` | 请求可回应，计划可在下期对照；未确认事项清楚标出 |
| 7 | 提供核对入口 | 〔来源 ID〕、〔定位/版本/日期〕、〔事实与专业核验状态〕、〔使用范围〕 | 〔消费端实际来源清单〕 | `appendix.source-register` | 重要判断能回到获准使用的具体来源 |

若实际任务有更多主线，重复主线更新页；若某线没有可核验更新，明确写出待核对内容与责任，不套用占位结论。协作事项过多时另拆行动页，避免缩小文字或遗漏期限、责任和影响。

## 7. 消费端试用与验收

试用应在消费端新任务或隔离的匿名样例任务中执行。先使用已固定、已登记这些能力的基础设施版本，并读取消费端自己的目录与授权约定。

1. **内容准备。**按会前输入表登记任务和来源，形成逐页计划。至少选取两条有实际关联的工作主线，能对照上期计划与本期结果；若使用匿名样例，始终保留样例标识。
2. **装配核对。**按 `expression.html-production` 选择兼容容器与页面，调用 `html.materialize` 先预览再应用。检查场景 ID、页面顺序、重复页面实例、固定基础设施提交和文件哈希记录。
3. **内容演练。**由主汇报人按页面完整讲述一次，核对听众能否复述总体变化、关键证据与限制、跨线影响，以及需要回应的事项。若必须依靠逐个打开技术附件才能理解项目总体判断，继续调整总报告。
4. **工程检查。**核对本地资源、来源关联与占位清理，运行 `html.viewport-check`；具备浏览器时检查桌面、窄屏、翻页和打印。需要 PDF 时另走导出步骤并核对分页。浏览器运行时不足的检查记录为 `not-run`，不以静态检查替代视觉检查。
5. **专业与整合评审。**各线负责人核验本线事实、数值和限制；项目经理检查总体判断、上期对照、跨线影响、里程碑和协作请求。未核验部分继续保留待确认状态。
6. **用途确认与记录。**对具体受众、用途和范围完成发布确认后，按消费端约定保存版本、来源与评审记录。制作完成不自动触发发送、提交、推送或发布。

试用至少留下四类证据：逐页内容计划、物料化记录、工程检查结果、专业核验与整合评审记录。验收应分别标出“结构是否支持主汇报”“来源是否可追溯”“专业内容是否核验”“工程表现是否检查”“当前用途是否获准”，避免把其中一项通过等同整份报告通过。

本说明描述设计与试用方法，不表示已经完成真实项目总报告、真实浏览器视觉检查、专业验收或对外发布。后续应根据消费端实际试用反馈，判断三种正文页的字段和布局是否足够；只有重复出现的结构需求才继续沉淀为共享资产。
