# 小组资产仓代建与初始化流程

本流程面向没有本地资产仓的新小组组长。它把 GitHub Template 建仓、递归克隆和已有的仓内初始化 Harness 接成一个连续 Agent 工作流，避免组长先手动建仓、执行 clone 命令、再切换工作目录。

## 入口与分工

组长从本文件链接打开[可直接转发的完整提示词](../harness/group-asset-repository/CREATE_AND_INITIALIZE.md)，将全文发给具有本地命令与文件操作能力的 Agent。提示词必须完整随消息提供，或以 Agent 可读取的公共原始文件链接提供；不能让 Agent 在尚未创建资产仓时先依赖基础设施 submodule 内的规则。

创建阶段使用已发布的公开模板仓 `suanhaitech/suanhai-team-group-asset-template` 生成独立小组仓；基础设施不是源模板的一部分副本，而是生成仓中 `.gitmodules` 指向的真实 Git submodule，实际版本由父仓 `160000` gitlink 固定。创建后递归克隆，并读取新仓根规则。随后由 `consumer.group-asset-onboarding` 负责真实小组信息访谈和文件化进度。两个 Harness 职责相接，不互相替代：

```text
完整提示词（仓外启动）
  → 参数及工具预检
  → GitHub Template Generate
  → 本地递归克隆
  → 核验 .gitmodules / gitlink / submodule HEAD / Manifest
  → 新仓 AGENTS.md
  → consumer.group-asset-onboarding
  → 保存候选、未知项、负责人确认和续接位置
  → 组长审核
```

## 建仓前置条件

- 当前 Agent 工具环境可以运行 Git、GitHub CLI `gh`、Python 3.10+ 及 Git 所需辅助命令；普通桌面终端可用，不代表 Agent 子进程也可用。
- Agent 子进程的网络策略允许访问 GitHub API 和仓库 HTTPS；例如 Codex 的 workspace-write 沙箱需在客户端中允许本次工作区访问网络。
- `gh` 已使用组长预期账号登录。只读检查不能可靠证明该账号的组织建仓权限；以模板生成 API 的实际结果为准。提示词不会获取、打印或保存凭据，也不会尝试提升授权范围。
- 组长提供小组正式名称、仓库短名及本地父目录。短名未提供时可提出候选，但应在持久外部创建前确认；本地目标子目录必须不存在。
- 仓库默认为 private。只有组长明确要求 public 才可公开；组织策略不接受选择时应停止，不自动改变可见性。
- 建议组长先将准备存放新仓的父目录作为 Agent workspace 打开，再发送提示词。Agent workspace 必须覆盖所选克隆父目录并允许读写；不要把已有资产仓或其他 Git 仓的根目录直接用作父目录。不要创建探针文件测试权限。如果沙箱不能访问该路径，应请求组长通过客户端正常机制开放目录，不能用写入探测或更宽权限绕过，也不能把原工作区中的操作说成已经在新仓根目录完成。

提示词已将“收到完整请求后创建一个新仓、克隆和写入本地候选上下文”定义为有限授权；只有必要字段齐备并通过预检后才执行，不逐条询问已授权范围内的命令。缺少名称、路径或其他必需值时集中询问。遇到 API 权限错误、名称冲突、目标路径冲突、网络失败或工具策略拒绝时停止、报告并保留现场，不以重组或换用更宽权限规避策略。

## 外部副作用边界

GitHub template generation 会创建持久远程仓库。提示词必须先核对目标组织、仓库标识和可见性，创建后报告 URL 与实际结果。若结果未知，不重复发起可能创建第二个仓库的请求。

初始化文件只保存在本地新克隆仓中并供组长审阅。创建仓的授权不代表负责人确认、业务提交或远程推送授权；组长审核后需要共享时，再另行明确授权 commit/push。Agent 不删除刚创建的仓库来假装回滚，不覆盖既有目录，不改基础设施 gitlink。

所有项目相关输入默认是候选，并注明来源和状态。负责人明确核对后才能记录为负责人确认；这仍是可追溯的自述记录，不构成平台身份认证。零项目是合法结果，不能为了让初始化显得完整而虚构项目、任务、作品或发布授权。

## 新机器端到端测试

使用一个新建的私有合成测试仓进行测试，不把演练输入带入真实小组：

1. 在一台没有小组仓工作副本的设备中，先将准备存放新仓的父目录作为 Agent workspace 打开；例如在测试机上使用 `D:\Works\Suanhaitech\Repos`，前提是它存在且不是另一个 Git 工作树。核实 Agent 工具环境的 Git、`gh`、Python 和账号；测试输入指定的预期账号为 `ChaosTHL`，如新机检测结果不同则停止确认；组织建仓权限以模板生成 API 的实际结果为准。
2. 将完整提示词连同以下合成测试输入一次发给 Agent；仓库可见性留空以验证 private 默认。组长授权 Agent 创建该单一私有测试仓和本地 clone，不给组织管理权限：

   ```text
   小组正式名称：Suanhai 建仓与初始化 E2E 合成测试组
   GitHub 仓库短名：group-asset-create-flow-e2e-20261029
   本地父目录：D:\Works\Suanhaitech\Repos
   预期 GitHub 账号：ChaosTHL
   小组定位：仅验证小组资产仓创建与初始化流程，不代表真实团队或项目。
   维护责任：合成测试组长（测试身份，不代表真实责任人）。
   协作对象：合成测试成员甲、合成测试成员乙。
   项目列表：当前没有需要登记的真实项目，保持项目索引为空。
   来源：以上内容均为本轮合成测试输入，不引用真实项目事实。
   记录要求：将以上信息标为“合成候选，待负责人确认”，不要记成真实身份或负责人确认。
   ```

   该仓库名在编写本测试说明时尚未存在；执行时仍由 Agent 按模板流程检查冲突。若名称已存在，不自动改名或覆盖，先停止并报告。

3. 观察 Agent 是否用 GitHub Template Generate 创建仓，使用 `git clone --recurse-submodules`，没有要求组长手工运行 API 或 Git 命令，也没有先克隆基础设施仓。
4. 核对生成仓 URL 和 visibility；父仓 submodule 条目为 `160000`，`.gitmodules` URL/path 正确，submodule HEAD 完全等于 gitlink；Manifest 和 onboarding 入口可读，按消费端规则运行的本地预检通过。
5. 确认 Agent 读取的是新仓根规则，分轮写入被标为“合成候选”的信息和待确认项；项目索引保持空；没有建立任务、作品或发布授权，没有 commit/push。
6. 在新会话中只说“继续初始化小组资产仓”，确认 Agent 从共享文件恢复候选状态、未知项和下一步，不依赖第一次会话记录。
7. 核对新仓 `git status` 和 submodule：预期只有初始化上下文本地改动，submodule 干净且版本不变。不要将测试内容推送；记录客户端、操作系统、Agent 命令环境的依赖可用性、完整 gitlink SHA、行为与偏差。

### 失败分支也要验证

- Agent 账号未登录或不能在组织建仓：在 GitHub API 创建前停止，不请求或修改组织权限。
- 用户名或仓库短名冲突：不覆盖、不改名重试、不创建个人仓。
- 本地目标目录已存在或沙箱不可写：创建前停止；如果远程仓已创建后才发生异常，则保留远程仓并报告。
- Agent 环境缺 Git、`gh`、Python 或必要的 Git 辅助命令：说明具体命令和环境差异；不静默安装，不将检查标成通过。
- `gh auth status` 报登录失败但 GitHub API 连接同时被网络策略拒绝：将认证标成无法验证，先请求通过客户端正常机制开放 GitHub 网络；不要误判 token 失效或反复登录。
- submodule 不可获取、gitlink 漂移、工作区脏或预检失败：停止访谈写入，保留 repo 和日志；不执行 `submodule add`、`update --remote` 或改写版本。

测试报告分开记录“GitHub API 建仓成功”“clone 和固定依赖核验成功”“Agent 规则路由成功”“初始化候选文件保存成功”“新会话续接成功”。CI 和结构检查不能代替 Agent 客户端中的真实命令执行与访谈，也不能证明其他账号有组织建仓权限。

## 可复用范围

该流程不依赖特定项目事实，适用于科研小组、项目小组和其他 Suanhai 小组。基础设施仓拥有提示词与流程规则；各小组的身份、项目上下文、来源、任务、作品、评审和初始化进度只进入各自的资产仓。大工项目资产仓迁移和项目资料导入不属于此初始化流程。
