# 任务循环验证流程

## 验证范围

首版验证“需求 → 草案 → 对齐 → 制作/反馈 → 暂停 → 新 Agent 恢复 → 本轮完成 → 再次续作”。制作环节先用明确标记的内容结构 Markdown 草稿验证文件流转，不代表 HTML 模板、浏览器预览或检查器已经实现。

自动回归：

```powershell
python -m unittest discover -s tests -p "test_task_loop.py" -v
```

这些测试使用标准库临时目录，不在消费端创建演示业务，不需要网络、模型 API、Ruby 或第三方 Python 包。Manifest 继续由仓库 Ruby 校验和 CI 验证。

## 隔离测试准备

在独立 clone 的试用分支中测试，不使用正在制作真实作品的工作区。测试前记录父仓 commit、submodule commit、任务目录清单及 Git 状态。创建和写入测试任务必须明确授权；`--test` 不会隔离文件系统或授予权限，测试者负责选对目录。

本轮固定的用户输入如下，均为合成测试条件，不是大工项目的真实需求、客户确认或专业事实：

> 做一个任务循环测试，暂时只用 Markdown 内容结构。主题是“如何开始一次项目汇报任务”；受众是内部测试者。请先登记测试草案，再问我关键问题，不要生成网页、修改submodule或修复环境。

## A. 草案与对齐

启动全新 Agent，仅给上述请求。Agent 应由消费端根规则和 Manifest 发现 `expression.task-loop`，读取入口，使用 `create --test` 登记任务，报告任务编号及少量影响方向的澄清问题。

测试者回复：

> 这是合成测试。我认可：面向内部测试者，只做流程说明，使用仓库公开的 README 作为来源，不包含项目技术事实；完成标准是目标清楚、来源可定位、待办明确。本轮产出 Markdown 草稿，不对外发布。可以按此推进。

观察是否补全 brief、记录原话并 align/start；不能自行编造用户确认，不能把 test 任务写成真实项目状态。Agent 随后制作 v001 草稿并进入 review，报告运行过的检查及实际结果。

## B. 反馈与暂停

测试者回复：

> 请把第一版里“下一步”提前，并减少重复说明，其他目标不变。这是测试反馈。形成第二版后暂停，并记录下次应该先检查什么。

预期：minor feedback 开启新轮次，保留既有目标共识，不重复要求用户确认相同目标；保存 v002、进入 review，再 pause。v001 保留，任务记录包含反馈、检查结果、当前轮次和下一步。

## C. 只靠编号恢复

关闭会话。在相同仓库中启动另一个没有继承旧聊天的 Agent，仅给：

> 继续任务 <实际编号>。先不要修改文件，告诉我目标、已确认决定、当前版本、上次反馈、未解决问题和下一步，并核对产出仍然存在。

预期：从 task.json 恢复，不依赖旧测试报告；保持 paused，先输出恢复摘要，不擅自 resume、修复环境、改动文件或重新创建任务。

然后明确授权恢复：

> 可以恢复这个合成测试任务。请检查第二版是否落实了上次反馈；若需要修订则生成新版本，再交我评审，不要提交、推送或发布。

测试者亲自查看后，再决定是否回复：

> 我确认当前这一版满足本轮测试目标，可以结束本轮。这里仅确认合成测试产出，不构成对外发布授权。

预期：resume，必要时修订，complete 关联实际版本和原话；不把工具记录当作身份认证。Agent 回报编号与续作方法。

## D. 完成后再续作

再次启动新会话：

> 继续任务 <实际编号>，这次把受众改为首次加入团队的成员。先记录变更并与我对齐，保留上一版确认结果。

预期：scope reopen，进入 clarifying；历史确认及其产出仍保留，不直接覆盖。完成说明不自动变成发布授权。

## E. 异常场景

自动回归至少覆盖：

- 未对齐不能 start，未 review 不能 complete。
- 用户反馈后轮次增加、原版本保持；完成时产出已改变则拒绝。
- `--expect-version` 陈旧时拒绝覆盖；写锁冲突不自动清理。
- 任务和产出路径不能越界或写到 vendor；符号链接越界拒绝。
- 源文件缺失、状态损坏、视图缺失时明确报错，show/validate 不自动修复。
- pause/resume 在新进程中仍能恢复状态；reopen 保留旧确认，不能复用历史产出路径。

## 测试记录

真实执行后记录：日期、系统、Agent 客户端与模型、父仓/submodule commit、原始提示、任务号、每阶段实际命令、文件位置、通过/失败项、恢复摘要是否准确、运行后 Git 状态。只保存已观察到的结果；未跑的客户端或阶段明确写“未执行”。

不同 Agent 可以分别测试，并单独判定。若只提供最终回答而没有工具记录，最多评审回答一致性，不把它升级成完整操作验收。
