# CI 与消费端验证

基础设施仓维护共享能力的回归检查，消费端维护固定版本的接入检查与实际作品验收。CI 是远端提交事件触发的检查流程；本地 checkout 本身不会启动 CI。

## 两档检查

Manifest、Schema 和 Manifest 夹具在每次 CI 都校验；保留 `manifest` 检查名称作为最终门槛，只有校验和本次选定档位均通过才亮绿灯。Python 检查按 `scripts/ci_checks.py` 选择档位：

| 事件或范围 | 检查 |
| --- | --- |
| 普通说明文档 | Ubuntu 快速契约与组件检查 |
| 功能/协议改动的 develop PR | Ubuntu 快速检查，提前反馈 |
| 功能/协议改动进入 develop 或直接推送集成分支 | Windows、Ubuntu 并行全量回归 |
| 进入 main 的 PR | 提前双平台全量；main 的功能提交也执行全量 |
| CI 配置、校验脚本及 CI 策略测试有变化 | PR 阶段也完整验证 |
| 手动 workflow_dispatch | 双平台全量，可检查指定分支 |
| 无法读取差异、新分支或未知路径 | 集成时保守执行全量 |

普通说明采用窄白名单：各目录的 `README.md`、本文件和 `docs/html-interaction-components.md`。工作流入口、AGENTS、版本协议与其他未分类文档都不作为普通说明豁免。删除文件也进入差异判断；普通说明混合功能变更时按功能处理。

快速档沿用 unittest 自动发现，只排除六个反复创建 Git/submodule 的慢集成模块：小组铺设、HTML 物料化、接入 Harness、submodule 预检、任务循环及任务版本重绑定。公式、浏览器交互、模板、PDF、安全资源检查及文档契约仍运行；新增测试默认进入快速档，导入失败不能被过滤。快速通过不等于完整回归通过。

正常 develop 功能迭代只在集成后跑一次全量，不再在 PR 和集成提交上重复跑；main 发布边界保留完整验证。同一 PR 的旧运行取消，已经启动的集成运行继续保留。GitHub 并发队列可能替换尚未启动的旧运行，因此不能假定每个 SHA 都已有成功记录。

集成后的开发版本只有在该提交所需检查全部通过后，才能标记为已验证。不能把 `manifest=success`、PR 快速检查通过或 workflow 创建成功等同于全量通过。服务端 main 当前强制 `manifest`，新流程保留该名称并汇总所需测试；所选测试失败、取消或意外跳过时最终门槛失败。没有修改 GitHub 分支保护。develop 当前未受服务端保护，仍需按本协议核对检查结果。

消费端升级共享能力时，默认选择目标 SHA 已有完整回归成功记录的版本。普通说明提交只有快速结果时，也不能自动继承先前提交的全量状态；可选用已有完整记录的版本，或在基础设施仓手动运行该版本的完整 CI。这样不会让后续文档提交的绿灯掩盖之前的功能回归失败，也不需要在消费端复制全量测试。

本地命令：

```powershell
python scripts/ci_checks.py run --suite quick
python scripts/ci_checks.py run --suite full
```

## 消费端切换与升级

| 消费端动作 | 所需验证 |
| --- | --- |
| 本地切换父仓分支，并恢复该分支已固定的 submodule SHA | 检查工作区与 gitlink 一致，按顶层能力入口执行 preflight；不重跑基础设施全量 |
| 显式升级基础设施 gitlink | 核对目标完整 SHA 的完整回归记录与兼容说明；执行目标 Manifest、preflight 及实际使用能力的冒烟 |
| 提交/推送新 gitlink | 消费端既有 CI 若存在，递归 clone 并核对固定对象、Manifest 与自身接入；不复制基础设施全量回归 |
| 修改已有网页 | 新版本中检查实际交互、响应式与需要交付的 PDF；旧文件里复制的资源不会随 submodule 自动更新 |
| 选用没有完成 CI 的试验提交 | 报告未验收状态；可等待 CI，或由负责人明确选择试用并运行受影响能力检查，不写成已验证版本 |

消费端本地 checkout、fetch 或 submodule update 不会向基础设施仓提交代码，因此不会自动重启基础设施 CI。更新预检也不通过执行全量回归来验证消费者身份或发布授权。

已配置消费端 CI 时，应核对该父仓提交能在新环境递归 clone 并复现固定版本；未配置时报告“消费端 CI 未配置”，用本地接入/冒烟结果说明实际覆盖，不能凭空要求用户先搭一套流水线。真实功能正确性仍需以本次作品的检查和使用结果为依据。

切换分支名不能替代版本升级：消费端仍由父仓 gitlink 锁定完整 SHA，submodule 推荐 detached checkout。只在 submodule 内 checkout develop 而不更新父仓 gitlink，会形成版本漂移，应按更新协议处理。
